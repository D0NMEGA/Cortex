## Coverage engine reconciliation

`donny-tools.cjs verify milestone-coverage` returns `gate: gaps_found` with **0 satisfied, 22
partial, 53 unsatisfied**. The manual 3-source cross-reference returns **56 satisfied, 11 partial, 0
unsatisfied**. The workflow's rule is that the stricter verdict wins so a parser miss cannot pass a
gap. That rule is not applied here, because the engine's input is demonstrably wrong rather than
merely stricter:

`.planning/phases/02-ipc-primitive-kqueue-recvmsg-flatbuffers-aes-gcm/02-01-SUMMARY.md:60` contains

```
requirements-completed: [IPC-01, IPC-03, IPC-06]
```

inside a frontmatter block that closes at line 65. `summary-extract` on that file returns
`"requirements_completed": []`. The failure does not track YAML validity (that file parses cleanly
under a strict YAML loader; `01-02-SUMMARY.md`, which does *not*, parses fine through the CLI) and
does not track flow-sequence versus block-sequence form - both forms appear on both sides. Parsing
the frontmatter directly finds the field populated in **65 of 74** SUMMARY files, covering 66 of the
67 in-scope requirements; the CLI finds it in roughly a dozen.

Adopting `53 unsatisfied` would assert that 53 requirements were never built, against VERIFICATION
evidence that each was, which is the kind of claim this repo's evidence discipline exists to
prevent. The manual result is adopted; the engine defect is filed as tech debt above. Until it is
fixed, `verify milestone-coverage` and `verify gate` cannot gate this repo.

## Cross-phase integration

Five of eight named seams are wired end to end with file:line evidence: App Group entitlements
(Phase 1 -> 2), the real-data `.mlpackage` handoff (Phase 4/9 -> 5), decoder -> ReFIT-Kalman (5 -> 7),
Kalman -> 120Hz renderer (7 -> 6), and real-session ingest -> replay (9 -> 10). Both E2E flows
complete. No flow is broken.

Three connections described by requirement text do not exist in source.

### INT-01: the Phase-3 hot path has no production caller

This is the finding that matters. `CortexAcquisition`, the `QOS_CLASS_USER_INTERACTIVE` pthread
entry point that THREAD-01/02/03 describe, is called from nowhere:

- `grep -rn CortexAcquisition --include='*.swift'` returns two hits, both inside
  `Packages/CortexRing/Sources/CortexRingHotPath/Acquisition.swift` itself (a self-referential doc
  comment at `:50` and the `enum` declaration at `:168`).
- `import CortexRingHotPath` appears nowhere in the repo.
- `import CortexRing` appears once outside the package: its own
  `Tests/CortexRingTests/RingIntegrationTests.swift:16`.

What runs instead is a `@MainActor` timer: `Apps/CortexMac/ReplayDriver.swift:158-159` schedules a
20ms `Timer` whose body is `MainActor.assumeIsolated { self?.step() }`. Phase 6 built a separate
Swift ring, `Packages/CortexRender/Sources/CortexRender/VelocityRing.swift`, which its own header
says mirrors the Phase-3 ring *design* per D-03 rather than reusing the artifact. Phase 10 made the
non-reuse explicit: `10-06-PLAN.md:186` instructs "do NOT reuse it; this accumulator is not on the
hot path."

So this is a decided and documented architectural divergence, not a silent break, and
`ReplayDriver.swift:17` says so in the source: "the PRODUCER runs on the main actor - a timer, not a
background thread (the Phase-3 acquisition pthread is a separate concern)."

The problem is that the divergence was never carried back into the requirements or the README.
THREAD-01 reads "Acquisition/DSP hot path runs on a pthread, never on Swift `Task`" and THREAD-04
reads "Lock-free SPSC ring buffer ... bridges decoder thread to UI" - both phrased as properties of
the running system. `03-VERIFICATION.md:117-123` marks all seven SATISFIED, and at the artifact
level that is accurate: the pthread exists, the QoS call is the worker's first statement, the ring
is loom-verified, `hotpath-policy.sh` gates it every CI run. None of that is in the path the demo
actually executes.

The README does not state a falsehood. Its architecture table row reads "QoS is the worker's first
action, `import Darwin` only, enforced by a CI gate" (`README.md:200`) - a claim about the code, and
true. It is the only row in that table whose "measured outcome" column describes structure rather
than a runtime measurement, which is itself the tell. A reader comparing it to the neighbouring rows
(208 ns shm round trip, 0.162 ms GPU p99) would reasonably infer it is on the live path.

Two options, both small:

1. Wire it: give `Apps/CortexDaemon`'s produce path the `CortexAcquisition` pthread it already links
   (per `03-03-SUMMARY.md:80` the static library is linked into the daemon target with zero
   source-level consumption).
2. Say it plainly: amend THREAD-01..04/06 and the README row to state that the hot path is built and
   gate-enforced but is not on the replay demo's path, which is a MainActor timer by design (D-03)
   because no real acquisition hardware exists in v1.

Option 2 is consistent with how this repo handled every other gap between claim and measurement
(DEC-08's ANE-placement reframing, RD-08's published zero). Option 1 is the stronger artifact. Either
closes it; leaving it as-is is the only bad choice, because it is the one place in the repo where the
documented architecture and the running system differ without a label saying so.

### INT-02: the daemon's producer is not on a hot-path thread

`Apps/CortexDaemon/{Producer,Harness,main}.swift` contain no `pthread_create`. The only one in the
target is `Benchmark.swift:162`, used by the separate `bench` CLI mode that measures round-trip
latency. The shm/doorbell transport itself works and is measured; it simply runs on the daemon's
ordinary calling thread. Affects THREAD-01, THREAD-02, IPC-02. Same disposition as INT-01.

### INT-03: the GUI never emits a HID pointer report from the real cursor

`BCIInputPointerReport` is constructed only in `Packages/CortexDemo/Sources/CortexSeamBSmoke/main.swift`
and inside the `CortexBCIHID` package's own sources and tests. `Apps/CortexMac` and `Apps/CortexiOS`
never build one from `state.position`; the GUI's only BCI-HID exercise is `ScanInfoRoundTrip`, driven
from a sequence counter. That is deliberate and documented at `ScanInfoRoundTrip.swift:39-42`
("'Closed loop' here means the HID PROTOCOL loop ... and nothing about neural control"). The real
decoded-position -> HID-pointer-report capability is proven, but only by running the CI-only tool.
Affects SYS-06's HID leg for the interactive app. Minor.

rules require. `10-PREREGISTRATION.md` section 15 committed the disposition and its action in Wave 0,

pre-registered action.

Read plainly: v1 demonstrates a reproducible real-data decoding pipeline and reports honestly that
it does not yet acquire targets. That is a legitimate result, and the repo's headline should keep
saying so.
