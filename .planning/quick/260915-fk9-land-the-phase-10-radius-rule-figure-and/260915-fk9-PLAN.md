## D-A: no new Python dependency. Keep the `--with matplotlib --with pillow` invocation.

`radius_rule_figure.py` needs matplotlib and pillow; neither is in `Decoder/pyproject.toml`.
**Decision: add nothing to `Decoder/pyproject.toml`.** The canonical command is

```bash
uv run --project Decoder --with matplotlib --with pillow \
  python Decoder/scripts/radius_rule_figure.py docs/media/radius-rule.gif
```

Rationale, in the order that decides it:

1. **The script can never run in CI anyway.** `ci.yml` asserts `Decoder/data` is empty on a CI
   checkout (`ci.yml:726-729`) and fails the build if it is not. This generator reads
   `Decoder/data/indy_20160630_01.mat` (382 MB, gitignored). A `figures` extra would install
   matplotlib and pillow into every CI job and every contributor's `uv sync` to support a script
   that only ever runs on a machine that already holds the dataset.
2. **It moves the pinned surface for nothing.** A new extra re-resolves `Decoder/uv.lock`, which CI
   cache-keys at `ci.yml:700-701` and prints as pinned versions at `ci.yml:708-711`, and which
   `Tools/scripts/toolchain-policy.sh` reasons about. This repo's whole toolchain posture is that
   the pinned surface moves only when a shipped artifact needs it. A figure does not.
3. `--with` keeps reproduction self-contained: the command in the script's docstring is the whole
   recipe, with no sync step and no lockfile state to match.

Cost of (a), and its mitigation: `--with` does not pin matplotlib/pillow versions. Mitigation is the
repo's normal one - Task 2 records the resolved versions in the evidence file, the same way
`04-training-evidence.md` records wheel versions. If the figure is ever regenerated and the output
differs, the evidence file says what it was rendered with.

## D-B: the 7.27 MB GIF ships as-is. No lossy recompression, no downscale, no crop.

Measured during this plan's discovery, on the actual artifact:

| variant | size | verdict |
|---|---|---|
| as rendered (PIL, 72-colour adaptive palette, optimize=True) | 7.27 MB | **ships** |
| `gifsicle -O3 --lossy=60` | 6.85 MB | 6% saving - not worth any artifact risk |
| `gifsicle -O3 --lossy=100 --colors 48` | 3.42 MB | rejected, see below |

Rejected because of what the saving costs. The artifact's load-bearing content is small monospace
text: the per-pane readout (`off cell centre +x.xxx, +y.yyy mm` / `disc FITS its cell`) at 8.4 pt and
the two honesty footers (full-session totals; the excerpt-selection rule, realtime marker and session
sha256 prefix) at 8.6-9.4 pt. Lossy GIF dithering degrades exactly that content first, and the only
setting that saves anything meaningful is the aggressive one. Trading legibility of the honesty
labels for 3.8 MB is the wrong trade in a repository whose stated discipline is that every published
number stays traceable and legible.

Why the size is acceptable in absolute terms: `.git` is 15 MB today (`size-pack` 11.08 MiB) and the
largest existing blob is ~1.05 MB, so this roughly doubles the pack. That cost is paid **once** - it
is a one-shot artifact, not a file that churns - the repo is private, there is no CI step that
fetches media separately, and the alternative (ship scripts only, regenerate on demand) means nobody
who clones the repo can see the figure, because regenerating it needs the 382 MB gitignored `.mat`.

Consequence to honor: do not add further animated variants later. One GIF plus two stills is the
budget. A second variant is a new decision, not a free addition.
