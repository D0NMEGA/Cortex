<objective>
Re-derive every CoreML-side number on the real-data checkpoint: the 4-bit palettization size ratio
and loss delta on both models, the ANE op-eligibility scan, and the decoder p99 with real weights.

Purpose: RD-05 and RD-06 forbid inheriting a number from the synthetic run. Research predicts the size
ratio should reproduce `04-palettization-evidence.md`'s 3.471x almost exactly, because the
architecture, parameter count and which tensors clear `weight_threshold=2048` are all unchanged - so a
materially different ratio means the conversion config drifted, and that is itself the finding. The
loss delta will NOT reproduce 0.009114, because k-means centroids are fit to the actual weights. Op
eligibility is a graph property invariant to weight values, so 226/226 with zero CPU-only should
reproduce exactly; any deviation means the traced graph changed and should stop the phase rather than
be papered over (D-17).

Output: `real_checkpoint.py`, real-weight-aware slow tests, `rederive_coreml.py`, the metrics JSON's
`palettization` / `ane` / `latency` sections, and `09-coreml-evidence.md`.

coremltools 9.0 `OpPalettizerConfig` defaults, read from the installed wheel:
`mode='kmeans', nbits=None, lut_function=None, granularity=PER_TENSOR, group_size=32,
channel_axis=None, cluster_dim=1, enable_per_channel_scale=False, num_kmeans_workers=1,

**`weight_threshold = 2048` skips any weight tensor with fewer than 2,048 elements. The velocity
readout is `2 x 96 = 192` elements, so the shipped model's velocity head is NEVER palettized.** D-16's
"R2 delta on the with-velocity model" is therefore entirely attributable to encoder palettization
propagating through an unquantized head, and the evidence must say so.

0.009114, 226/226 ops ANE-eligible with zero CPU-only, p99 approx 0.14 ms on M5 Pro (CPU-placed, the
