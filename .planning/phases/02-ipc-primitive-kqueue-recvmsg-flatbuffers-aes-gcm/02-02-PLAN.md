Implement the Foundation-free `CortexIPCTransport` hot path: (1) a fixed-stride POSIX shm ring in the App Group container (open/map via the existing `cortex_shm_open` shim, slot arithmetic from `CORTEX_CHANNEL_COUNT`, acquire/release `seq` counters, and the busy-poll read that is the actual sub-µs path per CF#2); (2) a `socketpair`+`kqueue` `EVFILT_READ` doorbell that carries only a tiny notification and serves as the idle/arming wake (D-01); and (3) cross-process FD handoff of the shm fd via a COMPLEX `mach_msg` with one `MACH_MSG_PORT_DESCRIPTOR` built from `fileport_makeport` — implemented as a C shim in `CortexCoreC` so the Transport Swift stays Foundation-free, with NO `SCM_RIGHTS` anywhere (SC#2). **Step 1 — Write the C shim header `cortex_fdmsg.h`** in CortexCoreC's include dir (so both CortexCore Swift and CortexIPCTransport can `import CortexCoreC`). Declare the message struct and two functions. Use the EXACT struct from RESEARCH.md Q1, extended with the ring geometry inline payload:

```c
#ifndef CORTEX_FDMSG_H
#define CORTEX_FDMSG_H
#include <mach/mach.h>
#include <stdint.h>

// IPC-03: cross-process FD passing via mach_msg + MACH_MSG_PORT_DESCRIPTOR (fileport).
// NO SCM_RIGHTS — this is the mandated Mach primitive, not the BSD socket-control-message path.
// Only the shm region fd is fileport-sendable (CF#5); never pass a kqueue/socket fd here.

typedef struct {
  mach_msg_header_t          header;       // msgh_bits |= MACH_MSGH_BITS_COMPLEX
  mach_msg_body_t            body;         // msgh_descriptor_count = 1
  mach_msg_port_descriptor_t fd_port;      // MACH_MSG_TYPE_MOVE_SEND, MACH_MSG_PORT_DESCRIPTOR
  uint64_t                   ring_bytes;
  uint64_t                   slot_stride;
  uint32_t                   slot_depth;
  uint32_t                   _pad;
  char                       shm_name[32]; // <=31 + NUL (PSHMNAMLEN)
} cortex_fd_msg_t;

// Send the shm fd (made into a fileport) + ring geometry to `dest` (a send right).
// Returns KERN_SUCCESS (0) or a mach_msg_return_t / -errno (fileport failure encoded as -errno).
int cortex_fdmsg_send(mach_port_t dest, int shm_fd,
                      uint64_t ring_bytes, uint64_t slot_stride, uint32_t slot_depth,
                      const char *shm_name);

// Receive on `rcv` (a receive right); reconstruct the fd via fileport_makefd; output geometry.
// Returns the received fd (>=0) or a negative error. Caller owns the returned fd (CLOEXEC set).
int cortex_fdmsg_recv(mach_port_t rcv,
                      uint64_t *out_ring_bytes, uint64_t *out_slot_stride,
                      uint32_t *out_slot_depth, char out_shm_name[32]);

#endif // CORTEX_FDMSG_H
```

<threat_model>
## Trust Boundaries (Plan 02-02 scope)

| Boundary | Description |
|----------|-------------|
| Producer process ↔ shm ring ↔ Consumer process | The mapped shm region is a shared mutable trust boundary: both processes read/write the same physical pages. A malformed seq or stride read by the consumer could index out of the mapped region |
| Sender ↔ Mach send right ↔ Receiver (FD handoff) | The shm fd is wrapped as a fileport and moved over a Mach send right; whoever holds that send right can inject an arbitrary fileport (i.e., hand the consumer an attacker-chosen fd) |
| Socket peer ↔ doorbell | The AF_UNIX socketpair peer can write arbitrary bytes to the consumer's kqueue-armed fd |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02-01 | Tampering | consumer reads a torn slot (producer mid-write) | mitigate | Acquire/release ordering: producer writes the slot THEN release-stores seq; consumer acquire-loads seq THEN reads the slot. RingTests asserts the ordering contract. The GCM tag (Plan 02-03) additionally fails-closed on any partial/corrupt slot |
| T-02-02-02 | Spoofing | a holder of the rendezvous send right hands the consumer a malicious fd via fileport | mitigate | The rendezvous send right is injected by the parent at spawn (CF#3 verdict, Plan 02-01) — not a global name an arbitrary process can look up; the consumer adopts the fd only from the single expected message. Defense-in-depth: the consumer validates the received ring geometry (ring_bytes/stride/depth) against the compile-time `CORTEX_CHANNEL_COUNT`-derived expectation before mapping |
| T-02-02-03 | Denial of Service | malformed shm_name (no NUL) overflows on the receiver | mitigate | `shm_name[32]` is fixed-size; `strncpy(.., 31)` + explicit NUL; receiver treats it as a bounded buffer. The shm name is also asserted ≤31 bytes at compile time (CORTEX_SHM_NAME assert) |
| T-02-02-04 | Information Disclosure | passing the wrong fd type (kqueue/socket) leaks a capability | mitigate | CF#5: only the shm fd is ever passed to `fileport_makeport`; `fileport_makeport` itself ERRORS on a kqueue/socket fd (man page), so a mistaken pass fails loudly rather than leaking |
| T-02-02-05 | Denial of Service | SIGPIPE from a dead doorbell peer kills the process | mitigate | `SO_NOSIGPIPE` set on both socketpair fds; writes to a closed peer return EPIPE instead of signaling. DoorbellTests proves the process survives |
| T-02-02-06 | Elevation of Privilege | Foundation/Obj-C runtime sneaks onto the hot path | mitigate | `hotpath-policy.sh` (re-scoped to CortexIPCTransport in Plan 02-01) gates every file here; all three sources are `import Darwin` only |
