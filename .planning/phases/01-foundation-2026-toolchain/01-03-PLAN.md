  <action>
Write a self-contained bash validator using only macOS-bundled `plutil` + `grep`. The script accepts variadic manifest paths (so CI can invoke it with both manifests in one call, and Phase 2/3 can add the daemon manifest with a one-line CI tweak). The script exits 1 (non-zero) if ANY manifest is invalid OR missing CA92.1 OR missing the NSPrivacyAccessedAPICategorySystemBootTime category.

Write `Tools/scripts/validate-privacy-manifest.sh` with this EXACT content:

```bash
#!/usr/bin/env bash
# Source: project-defined per CONTEXT.md D-14 / RESEARCH.md Q5.
# Purpose: validate Apple PrivacyInfo.xcprivacy manifests against project requirements.
#
# Phase 1 invariants enforced:
#   1. File is a valid Apple plist (plutil -lint clean)
#   2. NSPrivacyAccessedAPITypes array exists
#   3. NSPrivacyAccessedAPICategorySystemBootTime is declared
#   4. CA92.1 reason code is present (covers mach_absolute_time per Apple required-reason API list)
#
# When Phase 2/3 lands required-reason API usage beyond mach_absolute_time, extend the
# REQUIRED_REASONS array below. When the daemon target gets its own manifest, add it
# to the CI invocation in .github/workflows/ci.yml — argv is variadic.
#
# Exit codes:
#   0 — all manifests pass
#   1 — at least one manifest failed validation
#   2 — usage error (no manifests passed)
#
# Source for CA92.1 / NSPrivacyAccessedAPICategorySystemBootTime mapping:
# https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api
set -euo pipefail

if [[ $# -lt 1 ]]; then
  echo "usage: $0 <PrivacyInfo.xcprivacy> [more...]" >&2
  exit 2
fi

EXIT=0

for MANIFEST in "$@"; do
  if [[ ! -f "$MANIFEST" ]]; then
    echo "ERROR: $MANIFEST does not exist" >&2
    EXIT=1
    continue
  fi

  echo "checking $MANIFEST"

  # 1. Plist syntactic validity.
  if ! plutil -lint "$MANIFEST" >/dev/null; then
    echo "ERROR: $MANIFEST failed plutil -lint" >&2
    EXIT=1
    continue
  fi

  # 2. NSPrivacyAccessedAPITypes array exists.
  if ! plutil -extract NSPrivacyAccessedAPITypes raw "$MANIFEST" >/dev/null 2>&1; then
    echo "ERROR: $MANIFEST missing NSPrivacyAccessedAPITypes array" >&2
    EXIT=1
    continue
  fi

  # 3. NSPrivacyAccessedAPICategorySystemBootTime category declared.
  XML=$(plutil -convert xml1 -o - "$MANIFEST")
  if ! grep -q "<string>NSPrivacyAccessedAPICategorySystemBootTime</string>" <<< "$XML"; then
    echo "ERROR: $MANIFEST missing NSPrivacyAccessedAPICategorySystemBootTime category" >&2
    EXIT=1
    continue
  fi

  # 4. CA92.1 reason code present.
  if ! grep -q "<string>CA92.1</string>" <<< "$XML"; then
    echo "ERROR: $MANIFEST missing CA92.1 reason code (required for mach_absolute_time)" >&2
    EXIT=1
    continue
  fi

  echo "OK: $MANIFEST"
done

exit $EXIT
```

<threat_model>
## Trust Boundaries (Phase 1 — Plan 03 scope)

| Boundary | Description |
|----------|-------------|
| `PrivacyInfo.xcprivacy` (source) → app bundle (artifact) | The manifest must end up inside the built `.app` bundle's Resources directory, not just in source. RESEARCH.md Pitfall #7: a manifest can exist in source but be omitted from "Copy Bundle Resources" build phase, leading to App Store rejection in Phase 8 |
| validator script → CI gate (Plan 06 wiring) | The script's exit code is the entire gate; a regression where the script silently exits 0 on a broken manifest defeats FOUND-03 |
| user-facing privacy disclosure | A wrong reason code or missing category misrepresents the app's required-reason API usage to the App Store and downstream users |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03-01 | Tampering | `Tools/scripts/validate-privacy-manifest.sh` | mitigate | Script uses `set -euo pipefail` (any sub-command failure exits the script). Negative-control test in Task 2 Step 3 proves the gate bites when CA92.1 is removed. Plan 06 adds CI invocation; subsequent removal of the CI step would be visible in `.github/workflows/ci.yml` diff |
| T-01-03-02 | Information Disclosure | Privacy manifest content | accept | Manifests declare ONLY: NSPrivacyTracking=false, no tracking domains, no collected data types, one accessed-API category (SystemBootTime). This is the *minimum* possible disclosure surface; deviation upward (tracking enabled, data collected) would need explicit user decision and is out of scope for Phase 1 |
| T-01-03-03 | Repudiation | wrong reason code | mitigate | The script greps for the EXACT string `<string>CA92.1</string>` — no partial match, no whitespace flexibility. A different reason code would require an explicit edit visible in diff |
| T-01-03-04 | Denial of Service (build) | `plutil` not available | accept | `plutil` is bundled with macOS; absence implies a non-macOS environment which is already out of scope (Apple Silicon M4 only per AGENTS.md). On the macos-15 runner, plutil is always present |
| T-01-03-05 | Elevation of Privilege | declared but unused required-reason API | accept | NSPrivacyAccessedAPICategorySystemBootTime + CA92.1 grants no runtime privilege — it is a disclosure declaration, not a permission. The actual `mach_absolute_time()` call gate is at the syscall level (always available, no entitlement) |
| T-01-03-06 | Tampering | manifest stripped from bundle by mis-ordered XcodeGen sources | mitigate | RESEARCH.md Pitfall #7: post-build verification step in Plan 06 CI workflow runs `find ~/Library/Developer/Xcode/DerivedData -name PrivacyInfo.xcprivacy -path '*Cortex.app*'` and asserts ≥1 match. Catches the case where source has the manifest but the built app does not |

ASVS L1 controls applied: V14.3 (configuration — required disclosure metadata), V14.5 (HTTP request header validation — N/A here, but related "explicit declaration" principle).

Block on: high severity threats. None of the above are high — Plan 03 introduces no network surface, no auth, no input validation in source code (the manifest IS the input validation for App Store submission).
