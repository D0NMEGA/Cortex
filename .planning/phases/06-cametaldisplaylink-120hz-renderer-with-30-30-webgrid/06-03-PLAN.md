<objective>
Wire the two display-link adapters over the shared `WebgridFrameEncoder` (Plan 01) +
`CursorIntegrator`/`VelocityRing` (Plan 02). This is the single biggest architectural fact of the
phase (RESEARCH TL;DR #1): iOS and macOS use **different display-link plumbing**, so the renderer
needs **two thin adapters over one shared encode core**. iOS = `CAMetalDisplayLink` (vended
`update.drawable`); macOS = `NSView.displayLink(target:selector:)` → `CADisplayLink` (manual
`nextDrawable()`). Both run at locked 120Hz; both enforce ONE in-flight frame via a shared
`dispatch_semaphore(value: 1)` (RENDER-07, the deliberate latency-over-throughput divergence from
Apple's `value:3` sample). A SwiftUI-embeddable `WebgridView` hosts the layer + adapter so the app
targets render the grid.

Purpose: RENDER-01 (CAMetalDisplayLink iOS), RENDER-02 (120Hz), RENDER-07 (semaphore value:1),
RENDER-08 (NSScreen/NSView.displayLink macOS, no Catalyst). After this plan the grid actually
animates on screen, driven by the Lissajous producer — ready for Mac measurement (Plan 05).

Output: `FrameSynchronizer.swift`, `iOSDisplayLinkAdapter.swift`, `MacDisplayLinkAdapter.swift`,
`WebgridView.swift` in CortexRender, and the two app `ContentView.swift` files updated to embed
`WebgridView` + start a `LissajousProducer` feeding the ring.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Producer thread → VelocityRing → display-link callback thread | The synthetic producer pushes velocity on one thread; the display-link callback (iOS delegate thread / macOS run-loop thread) pops on another — the SPSC seam from Plan 02 (T-06-02-02). |
| Display-link callback → semaphore → GPU completion handler | The value:1 semaphore gates CPU encode against GPU completion; a wait/signal imbalance would deadlock. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-03-01 | Denial of Service | macOS `nextDrawable()` returns nil under `maximumDrawableCount=2` + `value:1` contention; if the skip path doesn't release the semaphore, the value:1 link DEADLOCKS (renderer freezes) | mitigate | The macOS skip path MUST balance every `waitForNextFrame()` with exactly one signal (Task 2 step 3 documents the invariant). With ≤0.4ms GPU there is enormous headroom so nil is rare, but the balance is enforced structurally, not by luck. RESEARCH Risk #5. |
| T-06-03-02 | Denial of Service | Drawable retention across frames (classic CAMetalLayer/`nextDrawable` stutter) holding the 2-deep pool | mitigate | macOS callback body wrapped in `autoreleasepool` so each frame's drawable is released promptly (RESEARCH Risk #6 / the SO/forum stutter cause). Grep-asserted. |
| T-06-03-03 | Tampering | A future maintainer "optimizing" `value: 1` → `value: 3` or `maximumDrawableCount` → 3, silently adding a frame (~8.3ms) of glass-to-glass latency (breaks PERF-04) | mitigate | Heavy anti-optimization annotation in FrameSynchronizer + MetalLayerConfig; the Plan-04 structural grep-gate asserts `value: 1` and `maximumDrawableCount = 2` and FAILS the build if changed (with a negative-control self-test). Defense-in-depth: comment + gate. |
| T-06-03-04 | Information Disclosure | Torn read of a partially-written `CursorVelocity` at the callback consumer | mitigate | Inherited from Plan 02's Acquire/Release SPSC ring (T-06-02-02); the callback only `pop()`s, which acquires the tail before reading the slot. No new exposure here. |

In-process, no network/auth/persistence. The new surface is the wait/signal balance (deadlock-safety) and the drawable lifecycle. Web-app threats do not apply.
