**The `identifier_name` trap, verified.** `Packages/CortexDemo/Sources/CortexDemoBench/main.swift`
declares `struct GlassToGlassReport: Codable` with fields `p50_ns`, `p99_ns`, `max_ns`, `count`,
`budget_ns`, `passed`, `device_annotation`, `methodology`, `note`. It is encoded with
`JSONEncoder` and `.sortedKeys`, so those property names ARE the JSON keys. The same pattern appears in
`Packages/CortexReFIT/Sources/CortexReFITBench/main.swift`'s `RefitBPS` and `WebgridBPSReport` (fields
including `reference_peak_bps` and, after Plan 10-11, `brain_gate_dense_9x9_bps`).

Two byte-identity checks depend on those keys:
- `ci.yml:378-388` diffs a fresh `--smoke` run's `.bench/refit_bps.json` against the committed
  `.planning/phases/07-refit-kalman-closed-loop-recalibration/refit_bps.json`.
- `Tools/scripts/bps-policy.sh:130` diffs a fresh run's `.bench/webgrid_bps.json` against the committed
  `.planning/phases/08-apple-bci-hid-integration-distribution-v0-ship/webgrid_bps.json`, and additionally
  requires the literal formula string and `"n_targets": 900` in it.

The fix that satisfies the linter and preserves the bytes:

    struct GlassToGlassReport: Codable {
      let p50Ns: UInt64
      // ... camelCase throughout ...
      /// The JSON keys are snake_case and are LOAD-BEARING: `refit_bps.json` and `webgrid_bps.json`
      /// are byte-diffed against committed artifacts by ci.yml and bps-policy.sh, so a key rename
      /// would fail those gates. CodingKeys keeps Swift camelCase (SwiftLint identifier_name) and the
      /// wire format snake_case (byte identity) at the same time.
      enum CodingKeys: String, CodingKey {
        case p50Ns = "p50_ns"
        // ...
      }
    }

`.swiftlint.yml` today: disables `line_length`, `todo` and `trailing_comma`; enables 17 opt-in rules;
sets `force_unwrapping: severity: error` with the comment "Force unwrap is BANNED - try! and as!
allowed in tests only"; `included: Apps, Packages`; excludes `.build` trees, `DerivedData`, the
generated Xcode project and workspace, `vendor` and `fastlane`.

`swiftlint --fix` (autocorrect) handles a subset of rules mechanically. `--strict` promotes warnings to
errors; it does NOT run analyzer rules (`unused_declaration`, `unused_import` need `swiftlint analyze`),
so those two opt-ins do not fire in CI today.

`blanket_disable_command` is itself an enabled rule, so a bare file-scope
`// swiftlint:disable file_length` with no re-enable is a violation. The scoped forms are
`// swiftlint:disable:this <rule>`, `// swiftlint:disable:next <rule>`, or a disable/enable pair around
a narrow region. A threshold change in `.swiftlint.yml` is the other legitimate option.
